# MALIUM 개발 인수인계 문서

> 작성일: 2026-09-30  
> 목적: Claude Code가 현재 구현 상태를 파악하고 다음 개발을 바로 이어갈 수 있도록 정리한 문서

## 1. 프로젝트 개요

MALIUM(말이음)은 실문법적 발화를 보이는 성인 실어증 환자를 위한 단계적 문장 산출 훈련 웹 앱이다.

훈련은 다음 순서로 진행한다.

```text
상황 이해
→ 핵심어 인출
→ 단어를 연결한 문장 구성
→ 문법 요소 선택
→ 도움을 제거한 전체 문장 재산출
```

단순 정답률보다 **어떤 단계에서 어느 정도의 도움을 받아 성공했는지**를 기록하는 것이 핵심이다.

MVP 대상은 성인 실어증 환자이며, 말실행증의 조음 운동 훈련 앱은 아니다.

## 2. 현재 프로젝트 구조

```text
MALIT/
├─ frontend/                 # Next.js 웹 앱과 서버 API
│  ├─ src/app/               # 화면과 Route Handler
│  ├─ src/components/        # 공통 UI
│  ├─ src/lib/               # 인증·Supabase·훈련 로직
│  ├─ public/training-images/# 18개 MVP 훈련 이미지
│  └─ scripts/               # 이미지 업로드 스크립트
├─ supabase/
│  └─ migrations/            # SQL 마이그레이션
├─ docs/                     # 기획·설계·검토 문서
├─ scripts/                  # 프로젝트 공용 스크립트
├─ README.md
└─ .gitignore
```

- 별도 `backend/`는 아직 없다.
- 현재 백엔드 역할은 `frontend/src/app/api`의 Next.js Route Handler가 담당한다.
- 별도의 음성 처리 서버나 배치 서버가 실제로 필요해질 때만 `backend/`를 추가한다.
- Git 저장소 루트는 `MALIT/`로 변경했다.
- 작업 트리는 기존 작업 내용이 많이 남아 있으므로 임의로 `reset`, `checkout`, 대량 삭제하지 않는다.

## 4. 계정과 역할

### 관리자

- Supabase Auth에서 최초 관리자 계정을 생성한다.
- 재활사 가입 신청을 승인하거나 반려한다.
- 훈련 주제와 훈련 콘텐츠를 관리한다.
- 사용자 목록을 확인한다.

### 재활사

- 웹에서 가입 신청한다.
- 관리자가 승인한 뒤 로그인한다.
- 환자 계정을 생성한다.
- 환자의 초기 훈련 레벨, 주제, 하루 훈련량을 설정한다.
- 필요할 때 설정을 변경한다.
- 환자별 훈련 기록을 조회한다.

### 환자

- 재활사가 계정을 생성한다.
- 현재 기본 비밀번호는 `00000000`이다.
- 환자가 직접 비밀번호를 바꾸는 기능은 구현하지 않는다.
- 초기 설정 이후 재활사가 매일 설정하지 않아도 자동으로 당일 훈련이 생성된다.

### 보호자

- 별도 보호자 계정과 전용 화면은 없다.
- 환자 옆에서 발화를 듣고 수동 확인 버튼을 눌러주는 보조자 역할이다.

## 5. 구현 완료 범위

### 5.1 로그인과 계정

- 환자·재활사·관리자 로그인
- 재활사 회원가입
- 관리자 재활사 승인/반려
- 이메일 확인 없이 가입 및 로그인하는 현재 MVP 흐름
- 재활사가 환자 Auth 계정과 프로필을 생성
- 역할과 계정 상태에 따른 화면 분기

### 5.2 환자 초기 설정과 자동 훈련 구성

- 레벨 1~3 선택
- 복수 훈련 주제 선택
- 하루 훈련 문장 수 설정
- 환자 등록 후 설정 수정 가능
- 설정에 맞는 게시 콘텐츠로 일일 훈련 계획 자동 생성
- 재활사가 매일 훈련을 새로 배정할 필요는 없음
- D1은 규칙 기반 구성이고, 기록 기반 AI 추천은 아직 없음

### 5.3 훈련 콘텐츠

- 6개 주제 × Level 1~3의 총 18개 초기 콘텐츠
- 훈련 이미지 18개 연결
- 관리자 콘텐츠 목록을 주제별, 레벨 순으로 정렬
- 콘텐츠의 문장 구조, 핵심어, 문법 목표 저장
- 동사 어간과 어미를 단순 문자열로 붙이지 않고 완성형을 별도로 저장
  - 예: `걷다 + 어요 → 걸어요`
  - 예: `청소하다 + 해요 → 청소해요`

### 5.4 환자 훈련 화면

- 상황 그림 관찰
- 핵심어 질문과 단계별 도움
- 핵심 단어를 이용한 문장 만들기
- 조사·동사 활용 선택
- 정답·오답 카드 테두리와 안내 표시
- 문법 결합 전후 형태 표시
- 도움을 제거한 전체 문장 재산출
- 훈련 완료 화면
- 환자 화면을 고려한 큰 글씨, 단순 문구, 베이지·연두 계열 UI

### 5.5 수동 발화 확인

훈련 시작 시 확인 주체를 고른다.

- 본인 확인
- 보호자 확인
- 재활사 확인

음성 인식은 아직 연결하지 않았다. 환자 발음이 불명확해 자동 인식이 실패할 수 있으므로 D2에서도 수동 확인은 유지해야 한다.

발화 후 다음 중 하나를 선택한다.

- 잘 말했어요
- 다시 해볼게요

### 5.6 수행 기록

다음 정보를 저장한다.

- 세션
- 콘텐츠
- 단계
- 목표 표현
- 도움 단계
- 성공 여부
- 확인 주체
- 세부 응답 데이터(JSON)
- 사용한 도움 이벤트
- 평가 기록

문법 단계에서는 추가로 저장한다.

- 첫 선택
- 최종 선택
- 전체 선택 이력
- 오답 횟수

전체 문장에서는 다음을 저장한다.

- 문장 도움 사용 여부
- 성공 또는 재시도
- 확인 주체

클라이언트 이벤트 ID로 동일 요청의 중복 저장을 방지한다.

### 5.7 재활사 훈련 기록 화면

- 환자별 카드 목록
- 환자 카드 클릭 시 날짜 목록 표시
- 날짜 카드 클릭 시 그날의 상세 로그 표시
- 같은 환자에서는 날짜 하나만 펼쳐짐
- 내부 코드 대신 한국어 단계명 표시
  - `keyword:subject` → `핵심어 · 주어`
  - `grammar:verb_ending` → `문법 · 동사 활용`
  - `sentence:full` → `전체 문장`
- 도움 없음, 도움 단계 사용, 문장 도움 사용 표시
- 도움 없이 성공, 도움 후 성공, 오답 후 성공, 다시 연습함 표시
- 본인·보호자·재활사 확인을 한국어로 표시

### 5.8 현재 환자별 요약 카드

현재 다음 값이 구현되어 있다.

- 최근 훈련일
- 완료한 전체 문장 수
- 수행 성공률
- 도움 없이 성공 비율
- 도움이나 재시도가 가장 많았던 단계

그러나 이 계산 방식은 아래 이유로 재설계가 필요하다.

## 6. 현재 고민 중인 핵심 사항: 재활사 관점의 요약 기록

### 6.1 현재 `수행 성공률`의 문제

현재 계산:

```text
success=true인 로그 수 ÷ 전체 로그 수 × 100
```

문제점:

- 핵심어, 문법, 전체 문장을 모두 동일한 1건으로 계산한다.
- 실패 후 재시도하여 성공하면 실패 1건과 성공 1건으로 각각 계산된다.
- 환자가 어느 단계에서 어떤 도움을 받았는지 충분히 설명하지 못한다.
- 재활사가 다음 훈련을 결정하는 데 직접적인 정보가 부족하다.

현재 `도움 없이 성공`은 성공 로그 중 단서, 문장 도움, 문법 오답이 없었던 로그의 비율이다. 이 역시 로그 단위 계산이어서 훈련 기회 단위 계산으로 바꿔야 한다.

### 6.2 권장 분석 단위

개별 로그가 아니라 하나의 **훈련 기회(trial)** 단위로 묶는다.

현재 데이터에서는 우선 아래 조합으로 묶을 수 있다.

```text
session_id + content_id + step
```

예를 들어 핵심어에서 재시도 후 성공했다면 로그 두 건이 아니라 다음 한 건으로 요약한다.

```text
핵심어·동작: 재시도 후 성공
```

장기적으로는 `trial_id` 또는 `attempt_group_id`를 DB에 추가하는 편이 더 안전하다.

### 6.3 우선 구현할 핵심 요약

#### A. 단계별 도움 의존도

각 언어 단계별로 다음 세 비율을 표시한다.

- 독립 수행
- 도움 또는 재시도 후 수행
- 미완료

분류 대상:

- 핵심어: 주어, 목적어, 동작, 장소
- 문법: 주격 조사, 목적격 조사, 장소 조사, 동사 활용
- 전체 문장

예시:

```text
핵심어·동작       독립 40% / 도움 후 50% / 미완료 10%
문법·목적격 조사  독립 20% / 도움 후 70% / 미완료 10%
전체 문장         독립 30% / 도움 후 60% / 미완료 10%
```

#### B. 도움 강도

단순히 도움 버튼 사용 여부만 보여주지 않는다.

- 평균 도움 단계
- 가장 자주 성공한 도움 단계
- 목표어 직접 제시까지 필요했던 비율
- 최근 도움 단계가 줄었는지 여부

어휘 도움 단계는 프로젝트 기획상 다음 구조다.

```text
자발 인출 → 범주 → 의미 특성 → 선택 → 음운 → 목표어
```

주의: 현재 코드의 도움 이벤트 유형은 `category`, `semantic`, `phonological`, `target` 중심이며 `선택` 단계가 명시적으로 빠져 있다. 실제 콘텐츠의 도움 배열과 표준 단계를 다시 맞춰야 한다.

#### C. 언어 영역별 어려움

다음과 같은 문장을 생성한다.

- 다른 영역보다 목적격 조사에서 더 많은 도움이 필요합니다.
- 명사보다 동작어를 떠올릴 때 단서가 더 많이 필요합니다.
- 핵심어는 독립적으로 말하지만 전체 문장 연결에는 도움이 필요합니다.

#### D. 어휘와 문장 결합의 차이

같은 콘텐츠에서 다음을 비교한다.

- 모든 핵심어 독립 성공 여부
- 문법 선택의 첫 시도 정확도
- 전체 문장 독립 재산출 여부

핵심어는 성공했지만 전체 문장에서 도움을 받았다면 `문장 결합 지원 필요`로 요약한다.

#### E. 최근 변화

한 번의 전체 비율보다 최근 세션 변화를 보여준다.

- 최근 3회와 이전 3회 비교
- 평균 도움 단계 변화
- 독립 수행 비율 변화
- 특정 조사나 동작어의 변화

표본이 부족하면 증가·감소를 단정하지 않고 `기록이 더 필요합니다`라고 표시한다.

권장 최소 기준:

- 비교 가능한 세션이 각 구간에 2~3회 이상
- 해당 단계의 훈련 기회가 최소 5건 이상

#### F. 레벨·주제별 수행

- Level 1~3별 독립 문장 완성
- 집안생활, 식사와 음료 등 주제별 도움 수준
- 특정 문장 구조에서 반복되는 어려움

#### G. 확인 방식

- 본인 확인
- 보호자 확인
- 재활사 확인

확인 방식별 기록 수를 함께 보여준다. 본인 확인과 재활사 확인을 완전히 동일한 신뢰도로 해석하지 않는다.

### 6.4 추천 화면 구성

환자 카드를 펼쳤을 때 다음 순서를 권장한다.

1. 쉬운 한 줄 요약
2. 가장 도움이 필요한 단계
3. 전체 문장 독립 완성 비율
4. 최근 평균 도움 단계와 변화
5. 단계별 `독립 / 도움 후 / 미완료` 분포
6. 날짜별 상세 로그 아코디언

기존의 단일 `수행 성공률` 카드는 제거하거나 보조 정보로 내린다.

### 6.5 표현 원칙

- `못함`, `실패가 많음`보다 `도움이 더 필요함`, `조금 더 관찰 필요`를 사용한다.
- 앱 훈련 결과를 임상 진단이나 일상 의사소통 능력으로 단정하지 않는다.
- 화면 하단 또는 요약 영역에 `앱 내 훈련 기록을 기준으로 한 요약입니다`를 표시한다.
- 실제 환자 검증과 언어재활사 인터뷰가 아직 없으므로 지표는 임상 확정 지표가 아니다.

- 환자 카드 내부 요약 UI 교체

#### 1단계 구현 결과 (2026-09-30)

- 계산 모듈: `frontend/src/lib/training/record-summary.ts` (순수 함수, 서버에서 계산 후 클라이언트로 전달)
- 훈련 기회: 같은 `session_id + content_id + step`에서 **성공이 나올 때까지의 연속 로그**를 1회로 묶는다. 성공 뒤 같은 단계가 다시 기록되면(새로고침 등) 새 기회로 본다.
- 분류
  - 독립: 첫 시도 성공 + 단서 0 + 문법 오답 0 + 문장 도움 없음
  - 도움·재시도 후: 그 외 성공
  - 미완료: 성공 없이 끝났고, 오늘 진행 중인 세션이 아님
  - 오늘 진행 중인 세션의 미해결 기회는 요약에서 제외하고 개수만 안내
- 도움 강도: 기회 안의 최고 `hint_level` (단서 위계 채점 방식). 핵심어는 1 범주 · 2 의미 · 3 첫소리
- 최근 변화: 끝까지 수행한 기회만으로 최근 3회 vs 이전 3회 비교. 각 구간 세션 2회·기회 5건 미만이면 `기록이 더 필요합니다`. 전체 10%p, 단계별 20%p, 단서 단계 0.3 이상 차이일 때만 변화로 표시
- 관찰 메모: 어휘-문장 결합 차이, 명사 vs 동작어 단서 차이, 상대적으로 어려운 문법 요소. 최소 표본 미달이면 생성하지 않음
- 판단 기준값은 `SUMMARY_RULES`에 모았다. 실제 환자 검증 전의 잠정 값이다.
- 기록 조회: `content_id` 추가, 1,000건 단위로 나눠 최대 10,000건 조회, 세션 완료 여부·콘텐츠 레벨·주제 함께 조회
- 남은 과제: "목표어 직접 제시" 단계와 기획상 `선택` 단서가 콘텐츠에 없어 해당 비율은 계산하지 않음(현재 최고 단서는 첫소리)

### 2단계 — 환자 훈련 결과 페이지 실제 데이터 연결

현재 `/patient/result`는 대부분 고정 문구다.

- 오늘 완료 문장 수
- 도움 없이 수행한 부분
- 도움을 받아 끝까지 수행한 부분
- 쉽고 부드러운 응원 메시지
- 임상 용어는 환자 화면에 노출하지 않음

#### 2단계 구현 결과 (2026-09-30)

- `/patient/result`를 서버 컴포넌트로 바꿔 오늘(KST) 마지막으로 완료한 세션을 읽는다.
- 1단계의 `groupTrials`를 재사용하고, `buildPatientDayResult`로 "혼자 해냈어요 N번 / 도움 받고 해냈어요 N번"과 문장별 결과를 계산한다.
- 비율·임상 용어는 표시하지 않는다. 응원 문구는 혼자 해낸 비중에 따라 3종 중 하나를 쓴다.
- 오늘 완료한 세션이 없으면 진행 중이면 "이어서 하기", 아니면 "오늘의 훈련으로"를 안내한다.
- 완료 후 재시작 문제 수정: `/api/training/daily-plan`이 `sessionStatus`(`completed`/`in_progress`/`not_started`)를 돌려주고, 오늘의 훈련 카드는 완료 시 "오늘 결과 보기", 진행 중이면 "이어서 하기"를 보여준다. `/api/training/sessions` POST는 이미 완료한 계획이면 409로 새 세션 생성을 막는다.
- 확인용 계정: 로그인 화면에 확인용 환자(`patient01`)와 재활사(`therapist01@malium.com`) 계정을 공개한다. 확인용 환자만 완료 후에도 "처음부터 다시 체험하기"로 같은 날 새 세션을 열 수 있다 (`isDemoPatientEmail`, `frontend/src/lib/auth/account-rules.ts`).

### 3단계 — 재활사 대시보드 실제 데이터 연결

#### 3단계 구현 결과 (2026-09-30)

- 기록 조회를 `frontend/src/lib/training/records-data.ts`의 `loadTrainingRecords()`로 분리해 대시보드와 기록 페이지가 함께 쓴다.
- 통계: 담당 환자 / 오늘 완료(오늘 시작 인원 함께 표시) / 7일 이상 미훈련(마지막 세션, 없으면 등록일 기준) / 살펴볼 환자
- "살펴볼 환자" 기준 = `PatientSummary.reviewReasons`가 있는 환자
  - 최근 3회 vs 이전 3회에서 도움 증가
  - 단계별 추세가 도움 증가
  - 최근 7일 안에 중단된 훈련 기회
- 담당 환자 표: 최근 훈련일, 오늘 상태, 살펴볼 점(없으면 요약 한 줄), 기록 보기 링크(`/therapist/records?patient=<id>`로 해당 환자 카드를 펼친 채 이동)

현재 일부 통계가 고정값이다.

- 오늘 훈련한 환자
- 오늘 완료한 환자
- 최근 7일 이상 훈련하지 않은 환자
